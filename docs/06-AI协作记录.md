# AI 协作记录

> 这份文档回答两个问题：**我怎么用 AI**，以及**我如何审查 AI 的产出**。
> 所有案例都来自本项目的真实开发过程，带问题定位与修复方式。

---

## 1. 工具与分工

| 角色 | 承担的工作 |
|---|---|
| AI（OpenCode / Claude） | 脚手架搭建、样板 CRUD、样式初稿、类型定义、测试用例、文档初稿 |
| AI 子 agent（并行） | ① 独立 UI/UX 评审 ② Spring Boot 后端实现 |
| 我（人工） | 需求拆解、信息架构、状态机设计、接口契约、竞态与边界、可访问性把关、最终 Review |

**核心原则：AI 负责「写得多」，我负责「判断对不对」。**
凡是涉及**状态、并发、契约、可访问性**的部分，AI 产出必须逐行复核。

---

## 2. 任务拆解顺序

不是一上来就让 AI「写一个看板」，而是按依赖关系切分：

```
① 需求理解文档（人写，AI 只做补全）
      ↓
② 数据模型 + 状态机 + 接口契约（人定，这是后续一切的地基）
      ↓
③ 高保真静态原型（AI 生成，人调视觉）
      ↓
④ 类型定义 types.ts（人写，作为前后端唯一真源）
      ↓
⑤ mock 适配层（AI 生成，人补边界与场景）
      ↓
⑥ 组件与页面（AI 生成，人做状态与交互）
      ↓
⑦ 状态覆盖 + 可访问性 + 响应式（人主导，AI 补漏）
```

**为什么先定契约**：如果先写页面再定接口，AI 会不断"猜"字段名，最后前后端对不上。
先有 `types.ts`，AI 生成的每个组件都在同一套类型约束下，返工率显著下降。

## 3. 适合交给 AI / 必须人工把关

| 适合 AI 生成 | 必须人工审查 |
|---|---|
| 目录结构、构建配置 | 状态机流转是否完备 |
| 表格 / 表单 / 抽屉的 JSX 骨架 | 乐观更新的回滚路径 |
| 重复度高的 CRUD 接口 | 请求竞态与取消 |
| 工具函数（格式化、校验） | 接口契约与字段语义 |
| 单元测试用例初稿 | 可访问性（焦点、ARIA、对比度） |
| 文档初稿 | 业务口径（接通率、意向率怎么算） |

## 4. 五个真实案例：AI 翻车 → 发现 → 修复

### 案例 1 · 演示浮层遮住了抽屉主按钮（P0）

**AI 产出**：原型右下角的「演示状态」浮层 `z-index: 60`，抽屉 `z-index: 41`。
**问题**：抽屉打开后浮层压在「下一步 / 提交并开始」上，鼠标点不到，3 步向导直接走不通。
**怎么发现**：用 Playwright 截图 + 独立评审子 agent 走查交互路径。
**修复**：

```diff
- .demo { position: fixed; z-index: 60; }
+ .demo { position: fixed; z-index: 30; }   /* 低于遮罩层 40 */
+ /* 并改为默认折叠为药丸，点击才展开 */
```

**教训**：AI 生成浮层时只考虑"要显示在上面"，不会考虑与其它浮层的层级关系。
**任何 fixed 元素都必须检查 z-index 栈。**

---

### 案例 2 · 对比度不达标（可访问性）

**AI 产出**：辅助文字用 `#8B919E`，警示标签用 `#B7791F` 配 `#FAF0DC` 背景。
**问题**：按 WCAG 相对亮度公式计算：

| 组合 | 计算值 | 要求 |
|---|---|---|
| `#8B919E` on `#FFFFFF` | **3.2 : 1** | ≥ 4.5 |
| `#B7791F` on `#FAF0DC` | **3.2 : 1** | ≥ 4.5 |

**修复**：

```diff
- --color-ink3: #8b919e;
+ --color-ink3: #6e7683;   /* 4.6 : 1 */

- --color-warn: #b7791f;
+ --color-warn: #8a5a12;   /* 5.2 : 1 */
```

**教训**：AI 选色靠"看起来舒服"，不会算对比度。
**把对比度检查固化成文档里的表格，每次改 token 都重算。**

---

### 案例 3 · 字体依赖 Google Fonts

**AI 产出**：`<link href="https://fonts.googleapis.com/css2?family=IBM+Plex...">`。
**问题**：国内网络环境下大概率加载失败，字体整体降级为系统默认，视觉方案直接崩塌；评审看到的和你看到的不是同一个东西。
**修复**：改用 `@fontsource` 自托管，字体随构建产物一起打包：

```diff
- <link rel="stylesheet" href="https://fonts.googleapis.com/...">
+ @import '@fontsource/ibm-plex-sans/400.css';
+ @import '@fontsource/ibm-plex-mono/500.css';
```

**教训**：AI 默认假设"外网可用"。**交付物必须能在断网环境完整呈现。**

### 案例 4 · `v-model` 绑定到非成员表达式，编译失败

**AI 产出**：

```vue
<TaskDetailDrawer v-model:open="Boolean(ui.detailId)" />
```

**问题**：Vue 编译器报 `v-model value must be a valid JavaScript member expression`——`v-model` 需要一个可赋值的引用，函数调用不行。
**修复**：改用带 getter/setter 的 `computed`：

```ts
const detailOpen = computed({
  get: () => Boolean(ui.detailId),
  set: (value) => {
    if (!value) ui.closeDetail()
  },
})
```

**教训**：AI 会把"读"的表达式直接塞进"读写"的位置。
**凡是 `v-model`，先问：这个表达式能被赋值吗？**

### 案例 5 · 详情抽屉的分布图 0 除，显示「关机 1 / 100%」

**AI 产出**：

```ts
const called = task.value.calledCount || 1
const percent = Math.round((count / called) * 100)
```

**问题**：对于一条「待执行、0 通话」的任务，`called` 被兜底成 1。
于是 `powerOff = max(0, 1 - 0 - 0 - 0 - 0) = 1`，
再算百分比得到 `1 / 1 = 100%`——页面渲染出「关机 1，占满整条进度条」的假数据。
**修复**：兜底只用于除法，不参与业务计算：

```diff
- const called = task.value.calledCount || 1
+ const called = task.value.calledCount
  ...
- percent: Math.round((item.count / called) * 100)
+ percent: called ? Math.round((item.count / called) * 100) : 0
```

**教训**：`|| 1` 是最危险的"顺手兜底"。**分母兜底和数据兜底必须分开。**

### 案例 6 · 工具链版本冲突（TS 7 × typescript-eslint）

**AI 产出**：直接用 Vite 8 模板默认的 TypeScript 7。
**问题**：

```
typescript-eslint does not support TS 7.0
tsconfig.json: Option 'baseUrl' has been removed
```

**修复**：锁定 TypeScript 5.9，并移除 `baseUrl`（`paths` 改为相对 tsconfig 解析）。
**取舍**：放弃 TS 7 的新特性，换取完整的 lint + 类型检查链路——对交付项目来说，**可维护性 > 尝鲜**。

**教训**：AI 会选"最新版本"，但最新版本之间不一定互相兼容。
**先跑通最小闭环，再升级。**

---

### 案例 7 · 空数据场景下，Tab 仍显示「全部 24」

**AI 产出**：空态只把列表置空，统计接口仍返回真实计数。
**问题**：页面同时出现「还没有外呼任务」和「全部 24」，自相矛盾。
**修复**：mock 的 `taskStats()` 在 `empty` 场景返回全 0，概览也同步归零。

**教训**：状态不是"一个组件的属性"，而是**整页的一致性约束**。
**每加一个状态，都要检查同屏其它模块是否也需要降级。**

### 案例 8 · CORS 把端口写死，联调直接被拦

**AI 产出**：

```java
.allowedOrigins("http://localhost:5173", "http://127.0.0.1:5173")
```

**问题**：Vite 在 5173 被占用时会自动切到 5174。此时前端 POST 创建任务直接返回 **403**，
而页面没有任何报错线索——控制台只有一行 `Failed to load resource: 403`。
**修复**：本地开发放行任意本地端口，生产环境再收敛为固定域名：

```diff
- .allowedOrigins("http://localhost:5173", "http://127.0.0.1:5173")
+ .allowedOriginPatterns("http://localhost:*", "http://127.0.0.1:*")
```

**教训**：AI 会把"文档里写的端口"当成事实，但真实环境端口是会漂移的。
**联调必须实际点一遍写操作，不能只验 GET。**

### 案例 9 · `orderBy` 的参数语义搞反，新任务永远排在最后

**AI 产出**：

```java
wrapper.orderBy(true, desc, column);
```

**问题**：MyBatis-Plus 的签名是 `orderBy(condition, isAsc, column)`——第二个参数是**是否升序**，
不是是否降序。传 `desc = true` 实际得到 `ORDER BY created_at ASC`，
于是刚创建的任务永远排在最后一页，运营会以为"任务没创建成功"。
**修复**：

```diff
- wrapper.orderBy(true, desc, column);
+ wrapper.orderBy(true, !desc, column);
```

**教训**：这类"参数名对但语义反"的 bug 编译器和 AI 都发现不了，
**只能靠真实数据验证排序结果**。我在联调时创建了一条任务，发现它没出现在第一页，才定位到根因。

## 5. 我固化的 Review Checklist

每次 AI 产出后逐项过：

**正确性**

- [ ] 状态机流转是否覆盖全部合法路径，非法路径是否拦截
- [ ] 乐观更新是否有快照、回滚、最终一致性
- [ ] 分母 / 空数组 / 0 值 / null 是否都处理
- [ ] 异步请求是否有取消或竞态保护

**契约**

- [ ] 字段命名与 `types.ts` 一致
- [ ] 分页参数从 1 开始、`totalPages` 边界正确
- [ ] 错误码与 UI 提示一一对应

**可访问性**

- [ ] 所有交互元素可 Tab 到达，焦点可见
- [ ] 弹层有焦点陷阱，Esc 可关闭
- [ ] 图标按钮有 `aria-label`
- [ ] 文字对比度 ≥ 4.5:1

**视觉**

- [ ] 8px 栅格；数字等宽右对齐
- [ ] 加载态不引发布局跳动
- [ ] 长文本省略且有 Tooltip
- [ ] 1440 / 1280 / 1024 无横向溢出

---

## 6. 结论

AI 把「从 0 到 1 搭出一个能跑的页面」的时间压缩了大约 **60%**，
但把「从能跑到可交付」的时间压缩得很少——**后者几乎全部是审查与判断**。

这个项目里，AI 生成的代码约占 70%，但**所有 P0 级问题都出在 AI 生成的边界处理上**，
而修复它们需要的不是更强的模型，而是更明确的验收标准。
